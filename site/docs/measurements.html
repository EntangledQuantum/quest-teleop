This page is docs/MEASUREMENTS.md from the repository.

"Latency" is the protocol's echo latency: from the moment the client samples the controllers to the moment it holds the simulator state that resulted from that sample. The client measures it and reports it back every frame; the status page splits it into its parts. It includes the wait for the next simulation step and the step itself, and excludes the display's own scan-out (about one refresh, 13.9 ms at 72 Hz).

Loopback, bundled demo (no headset) #

quest_teleop.probe against quest_teleop.demo. Scene: 17 nodes, 7 meshes, one 196-vertex cloth, one 40-point rope. Definition: 10 kB, loaded in 1 ms. Client input at 72 Hz.

No frame was lost in any run. Almost all of the latency is the server hold: an input waits on average half a simulation period for the next step, plus the step time. The network and the encoding add about 0.1 ms on loopback. With 30 % of the state datagrams dropped on purpose the client's state still converges to the server's, without retransmission (tests/test_loopback.py).

Quest 2 #

Quest 2, system software v209 (Android 14), 72 Hz, passthrough on. The headset app ran on the first install: OpenXR session, 1440 x 1584 sRGB swapchains with 4x MSAA, Touch controller bindings, passthrough layer; 72 / 72 frames per second with no stale frames, application GPU time 6.4 ms (before shadows were added; not re-measured since).

Latency on the headset is quantised to display frames (13.9 ms). With a slow simulator the latency is the simulator step plus one to two display frames. Wi-Fi costs nothing at the median; now and then a frame arrives one or two display frames late.
